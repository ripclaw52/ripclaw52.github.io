Why This Architecture?

The project separates gameplay into independent states:

  • Overworld
  • Battle
  • Menu
  • Cutscene

The project uses a state-driven architecture to separate gameplay systems such as battles, menus, cutscenes, and overworld exploration into isolated game states. This approach improves organization and simplifies transitions between gameplay screens. This prevents gameplay systems from becoming tightly coupled and allows new systems to be added with minimal impact on existing functionality.

Scriptable Objects are heavily utilized throughout development to store reusable data such as Pokémon species, move definitions, status conditions, type information, and UI references. This allows designers to modify gameplay data without directly changing core gameplay scripts.

Bug Fixes & Challenges

Health Bar Scaling Issue

Problem: Battle UI health bars rendered incorrectly at certain resolutions.

Solution: Adjusted battle camera configuration and normalized prefab scaling.

Result: Consistent UI rendering across battle scenes.

Animation Array Crash

Problem: Missing animation references caused runtime exceptions.

Solution: Added validation checks during initialization and update cycles.

Result: Improved system stability and reduced runtime crashes.

Pokédex Runtime Persistence Bug

Problem: Encounter data was persisting between Unity editor sessions.

Solution: Created dedicated runtime PokedexObject classes separate from ScriptableObject definitions.

Result: Player progress correctly resets and loads without affecting source data.
